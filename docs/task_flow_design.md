# タスクフロー設計: 調査エージェント（文章 + 画像）

- 作成日: 2026-10-28
- 状態: ドラフト（レビュー待ち）
- 位置づけ: LangGraph で実装する前に、具体例からタスクの流れを設計する。
  横と縦の役割分担は 3 章、再帰は 10 章、実装方式（ノード・状態）は 11 章に示す。

## 1. 目的

利用者がある物事について調査を依頼すると、AI が **正確な文章** と **正確な画像** を提供する。

設計の基本方針は次の 4 つ。

| # | 方針 | 理由 |
|---|---|---|
| P-1 | **依頼の段階で、不明な点は推測せず利用者に質問する** | 対象を取り違えると、文章も画像もすべて誤りになる |
| P-2 | **画像は複数の方法で探し、検証してから出す** | 一般的な画像検索や LLM は、マイナーな対象の画像に弱い。名前が合っていても別物の画像が混ざる |
| P-3 | **見つからない・確かめられないときは、正直に申告する** | もっともらしい誤りは、「見つからなかった」より有害。別物の画像を本物として出したり、画像を生成して代用したりしない |
| P-4 | **横の調査（網羅）はプログラムが、縦の調査（深掘り）は LLM が担当する** | LLM は多くのものを漏れなく扱うのが苦手で、1 つのことを深く読み解くのが得意。それぞれの得意な側に仕事を振る（3 章） |

## 2. 具体例（設計の出発点）

フローは以下の 4 つの例を、すべて正しく扱えるように設計する。
（例の対象は、フローの動きを説明するための仮のもの。事実関係は実装後のテストで確認する）

### 例 A: 同名の対象がある（質問が必要）

> 「マーキュリーについて調べて、画像もつけて」

- 惑星（水星）・ローマ神話の神・元素（水銀）・NASA の計画・自動車ブランド・人物（フレディ・マーキュリー）などがあり、対象が決まらない
- **期待する動き**: 調査を始める前に「どのマーキュリーですか？」と候補を挙げて質問する

### 例 B: マイナーな対象（画像探しが難しい）

> 「〇〇大学の △△ 研究室の××教授についての情報と画像を教えて。」

- 文章の情報は大学のwebページや研究者情報に少しある。写真は一般の画像検索では出てこないか、別の学校の写真が混ざる
- **期待する動き**: 複数の方法で画像を探し（8 章）、出典ページの説明文と照合して確かめる。
  確かめられなければ「見つからなかった。試した方法は〜。大学への問い合わせなどが考えられる」と申告する

### 例 C: 型番・品種など細かい違いが重要

> 「カメラの〇〇 EE17 について調べて、外観の写真を」

- よく似た兄弟機種（EE、EE28 など）の写真が検索結果に多く混ざる
- **期待する動き**: 文章調査で「その機種を見分ける特徴」（ロゴ、レンズの表記など）を先に集め、画像がその特徴と合うかを確かめる。
  見分けられない場合は「兄弟機種の可能性あり」と明記する

### 例 D: 実現できないことがはっきりしている

> 「昨日の研究室のミーティングのホワイトボードの写真を探して」

- 公開されていない情報なので、Web 調査では原理的に見つからない
- **期待する動き**: 調査を始める前、または計画の段階で「公開情報からは見つけられない」と伝え、時間をかけて探し回らない

## 3. 設計の中心: 横はプログラム、縦は LLM

### 3.1 LLM の得意・不得意

| | 横の調査（網羅） | 縦の調査（深掘り） |
|---|---|---|
| 内容 | 多くの観点・情報源・検索結果を、漏れなく・同じ基準で扱う | 1 つのページ・1 つの問い・1 つの画像を、深く読み解いて判断する |
| LLM の傾向 | **苦手**。一度に多くを渡すと、途中を読み飛ばす、観点を忘れる、試したことを覚えていない、数え間違える | **得意**。文章の意味を読み取る、根拠をたどる、矛盾に気づく、特徴を照合する |
| このシステムでの担当 | **プログラム**（チェックリスト・テンプレート・表・記録） | **LLM**（1 回の呼び出しで 1 件だけを扱う） |

### 3.2 仕事の振り分け

| 仕事 | 担当 | 理由 |
|---|---|---|
| 調べる観点を漏れなく挙げる | プログラム（観点チェックリスト） | LLM に「観点を全部挙げて」と頼むと、毎回違う・抜ける |
| 検索の言葉を作る（言語・別名・接尾辞の組み合わせ） | プログラム（テンプレート） | 組み合わせを漏れなく作るのは機械的な作業 |
| 情報源を順に全部試す | プログラム（情報源チェックリスト） | LLM に選ばせると、途中で諦める・同じものを繰り返す |
| 重複の除去・数え上げ・出典数の集計 | プログラム | LLM は数え間違える |
| 試したことの記録 | プログラム（`attempts_log`） | 「何を試したか」の申告（9 章）を正確にするため |
| 対象の種類の判定（人物・場所・生物・製品…） | LLM（短い判定） | 観点チェックリストを選ぶための小さな判断 |
| ページを読んで事実を抜き出す | LLM（1 ページずつ） | 深い読解 |
| 参照先をたどって一次資料を確かめる | LLM（1 本の流れを深く） | 深掘り |
| 画像候補が対象かを判断する | LLM（1 候補ずつ） | 深い照合 |
| 不足の発見 | プログラム（網羅表の穴）+ LLM（1 件ずつ質の判定） | 「何が足りないか」は表で機械的に、「質が十分か」は LLM で |
| 報告を書く | LLM（整理済みの材料から） | 材料はプログラムが絞り込んで渡す |

### 3.3 LLM の使い方のルール

| # | ルール |
|---|---|
| M-1 | **1 回の呼び出しで扱うのは 1 件だけ**（1 つの問い × 1 つのページ、または 1 つの画像候補） |
| M-2 | 「全部挙げて」「この 30 件をまとめて」のような横の仕事を LLM に頼まない。必要なら 1 件ずつ処理してプログラムで集める（map → プログラムで集約） |
| M-3 | LLM の出力は決まった形（JSON）にし、プログラムが集約・検査できるようにする |
| M-4 | 事実を抜き出すときは、根拠となる **原文の引用** を必ず付けさせる。プログラムがその引用が本当にページにあるかを照合し、ない場合は捨てる（作り話の防止） |
| M-5 | LLM に渡す文脈は、その 1 件に必要なものだけにする（調査全体の経緯を毎回渡さない） |

## 4. 全体フロー

```
[利用者の依頼]
      │
      ▼
① 依頼の分析（LLM）──── 対象の種類・目的・範囲・画像の要件を書き出す
      │
      ▼
② 不明点の判定（LLM）──(不明点あり)──▶ ③ 利用者に質問 ──▶ ② に戻る（最大 2 往復）
      │
      ▼
④ 実現可能性の判定（LLM）──(明らかに不可能)──▶ ⑪ 正直に申告して終了
      │
      ▼
⑤ 横展開（プログラム）
   観点チェックリスト × 検索の言葉テンプレート × 情報源チェックリスト
   → 検索を実行 → 重複除去・足切り → 「深掘りタスク」の一覧（キュー）を作る
      │
      ▼
⑥ 深掘り（LLM、1 タスク 1 件ずつ・並行）
   文章: ページを精読 → 引用付きで事実を抽出 → 参照先をたどる（縦の再帰）
   画像: 1 候補ずつ、掲載ページの文脈と画像の特徴を照合
      │
      ▼
⑦ 引用の照合（プログラム）──── 引用がページに実在しない事実は捨てる
      │
      ▼
⑧ 集約（プログラム）──── 網羅表の更新、出典数の集計、食い違いの検出
      │
      ▼
⑨ 不足の判定
   プログラム: 網羅表の穴（出典 0〜1 件の観点、合格画像 0 枚）を列挙
   LLM: 不足 1 件ずつ、「さらに深掘りすべきか / 別の言葉で探すべきか」を判断
      │
      ├──(横の不足: 観点・言葉・情報源が足りない)──▶ ⑤ へ（横の再帰）
      ├──(縦の不足: 1 件の根拠が弱い)──────────▶ ⑥ へ（縦の再帰）
      ├──(新しい曖昧さを発見)─────────────────▶ ③ へ
      │(不足なし / 上限 / 新しい情報が出なくなった)
      ▼
⑩ 報告の作成（LLM）──── プログラムが絞り込んだ材料（網羅表・合格した事実と画像・申告事項）から書く
      │
      ▼
⑪ 報告 ──── 文章（出典付き）+ 画像（出典・確信度付き）+ 見つからなかったものの申告
```

## 5. ②③ 不明点の判定と質問

### 5.1 何を確認するか

依頼を次の項目に分解し、**結果が変わってしまう不明点だけ**を質問する。

| 項目 | 確認する内容 | 不明なときの例 |
|---|---|---|
| 対象の特定 | 同名・似た名前のものがないか | 例 A「どのマーキュリー？」 |
| 目的・用途 | 何に使うか（発表、レポート、個人の興味など） | 文章の詳しさ・書き方が変わる |
| 範囲 | 時期・地域・側面（歴史、仕組み、現状など） | 「〇〇の歴史」か「〇〇の現在」か |
| 画像の要件 | 写真か図か、時代、枚数、使い道（公開資料に載せるか） | 公開資料に使うならライセンスの確認が必要 |
| 出力の形 | 文章の長さ、箇条書きか文章か、言語 | 指定がなければ既定値（5.3）で進める |

- 対象の特定では、プログラムが先に Wikipedia / Wikidata の API で曖昧さ回避ページと同名の項目を調べ、SearXNG の infobox も合わせて、同名の候補を LLM に渡す。
  LLM の知識だけで「同名のものはない」と判断させない（横の仕事のため）。

### 5.2 質問のルール

| # | ルール |
|---|---|
| Q-1 | 質問は 1 回にまとめて出す（最大 3〜4 問）。小出しに何度も聞かない |
| Q-2 | できるだけ選択肢を付ける（例:「1. 惑星の水星　2. ローマ神話の神　3. その他」） |
| Q-3 | 調べればわかること（一般的な事実）は質問しない |
| Q-4 | 質問は最大 2 往復まで。それでも決まらない点は、前提を明示して進める |
| Q-5 | 利用者が「おまかせ」と答えた場合は、置いた前提を最終報告の冒頭に書く |
| Q-6 | 依頼が明確なときは質問せずに進める（質問しすぎない） |

### 5.3 既定値（質問しないときに使う）

| 項目 | 既定値 |
|---|---|
| 文章の長さ | 400〜800 字程度 + 要点の箇条書き |
| 画像 | 対象がはっきり写っている写真 1〜3 枚 |
| 言語 | 依頼と同じ言語 |

## 6. ⑤ 横の調査: 網羅をプログラムで保証する

### 6.1 観点チェックリスト

LLM には対象の **種類** だけを判定させ（①）、調べる観点はプログラムが種類ごとのチェックリストから展開する。

| 対象の種類 | 観点（例） |
|---|---|
| 場所・建造物 | 名称と別名、所在地、建設・設立年、歴史の主な出来事、現状（現存 / 解体）、外観の特徴 |
| 生物 | 和名・学名・別名、分類、分布、形態の特徴、似た種との違い |
| 製品・機械 | 正式名・型番、メーカー、発売年、仕様、兄弟機種との違い、外観の特徴 |
| 人物 | 氏名と別名、生没年、所属・経歴、業績 |
| 出来事 | 名称、日時、場所、経緯、結果・影響 |
| 組織 | 名称と旧称、設立年、所在地、活動内容、沿革 |

- 依頼の「範囲」（5.1）で指定された観点を優先し、指定外の観点は簡単に済ませる。
- **外観の特徴** と **似たものとの違い** は、画像の検証（8 章）に使うので、画像を求められたら必ず含める。

### 6.2 検索の言葉の展開

プログラムがテンプレートで組み合わせを作る。LLM には「別名・学名・型番などの候補を 1 ページから抜き出す」だけを頼む（縦の仕事）。

| 要素 | 例 |
|---|---|
| 名前 | 正式名、別名、旧称、学名、型番、英語名（調査中に見つかったら追加。10 章 R-3） |
| 観点の言葉 | 「歴史」「沿革」「写真」「外観」「仕様」など、観点ごとに定義 |
| 絞り込み | 所在地、年代、メーカー名など、対象を特定する言葉 |
| 除外語 | 別物と判明した名前（10 章 R-4） |

### 6.3 情報源の Tier と調べる順番

情報源（サイト・ドメイン）を信頼度で 5 段階の **Tier** に分け、**上の Tier から順に** 調べる。
上の Tier で観点が埋まれば、下の Tier には降りない。LLM に「どこを調べるか」を選ばせず、プログラムが順番を決める。

#### Tier の定義

| Tier | 区分 | 例 | 使い方 |
|---|---|---|---|
| **1** | 一次情報・公的機関・学術 | 政府・自治体（`go.jp`, `lg.jp`）、大学・研究機関（`ac.jp`, `edu`）、学校（`ed.jp`）、対象自身の公式サイト、学術論文（CiNii Research, J-STAGE）、図書館・博物館・公文書のデータベース（国立国会図書館、ジャパンサーチ、文化遺産オンライン） | 最初に調べる。単独でも有力な出典 |
| **2** | 編集・審査された二次情報 | 百科事典（Wikipedia, Wikidata, Wikimedia Commons）、専門データベース（GBIF, iNaturalist）、主要な報道機関、出版社・学会のページ | Tier 1 の次に調べる。Tier 1 と組み合わせて確かめる |
| **3** | 専門性のある個人・団体 | 研究者・学芸員の個人ページ、郷土史家・愛好会のサイト、業界団体、専門的なフォーラム | Tier 1〜2 で埋まらない観点だけ調べる。マイナーな対象の一次情報が見つかることがある |
| **4** | 一般の二次情報 | 一般のブログ、旅行・解説記事、Q&A サイト、SNS | Tier 1〜3 で埋まらない観点だけ調べる。単独では「確認済み」にしない |
| **5** | 転載・量産・商用 | Pinterest、まとめサイト、アフィリエイト、量産記事、画像の転載サイト、ショッピングサイトの商品説明 | **出典としては使わない**。元の出典を探す手がかりにだけ使う |

- Tier の一覧は設定ファイル（例: `config/source_tiers.yaml`）としてプログラムが持つ。一覧にないドメインは、ドメインの種類で仮の Tier を決める（`go.jp` → 1 など）。どれにも当たらなければ Tier 4 とする。

#### 調べる順番

```
観点ごとに:
  Tier 1 を検索（site: 指定の検索 + Tier 1 のデータベース API）
    → 観点が埋まった？ ── はい ──▶ この観点は終了
    → いいえ
  Tier 2 を検索 → 埋まった？ ── はい ──▶ 終了
    → いいえ
  Tier 3 を検索 → 埋まった？ ── はい ──▶ 終了
    → いいえ
  Tier 4 を検索 → 埋まらなければ「出典不足」として網羅表に残す
  （Tier 5 は検索結果に出ても出典にしない。元の出典の手がかりとしてだけ記録する）
```

- Tier 1〜2 は、既知のドメインを `site:` で指定した文章検索と、データベースの API（6.6）で狙って調べる。学術の出典は SearXNG の学術カテゴリで探す。
  Tier 3〜4 は一般検索を行い、結果のドメインを Tier で分類する。
- 画像の探索（8.1）も同じで、候補は掲載ページの Tier の順に深掘りする。

#### 「観点が埋まった」の基準

| 状態 | 条件 |
|---|---|
| **確認済み** | 独立した出典が 2 つ以上あり、少なくとも 1 つが Tier 1〜2。または Tier 1 の一次情報が 1 つあり、他の出典と矛盾しない |
| **出典不足** | 出典が Tier 3〜4 だけ、または出典が 1 つだけ |
| **未発見** | 出典なし |

- 「確認済み」になった時点で、その観点は下の Tier に降りない（検索回数の節約）。
- 「出典不足」のまま Tier 4 まで調べ終えた観点は、報告の「確認できなかったこと」に書く。

#### Tier の調整

ドメインの Tier は出発点で、次の場合はページ単位で 1 段だけ上げ下げする。

| 調整 | 条件 | 判定 |
|---|---|---|
| 1 段上げる | Tier 3〜4 のページが、出典・資料名を明記した一次情報（例: 郷土史家が原資料を写真付きで紹介） | LLM（ページの精読、7 章） |
| 1 段下げる | Tier 1〜2 のページでも、内容が古い・他の出典の転載・出典なし | LLM（ページの精読） |
| 観点ごとの例外 | 例: 製品の **仕様** はメーカー公式を Tier 1 とするが、製品の **評価** ではメーカー公式を Tier 4 とする | 設定ファイルに観点ごとに定義 |

- 転載の見分け: 文章がほぼ同じページ（Wikipedia の写しなど）は、プログラムが文章の類似度で検出し、独立した出典として数えない。
- 将来は、検証の結果（そのドメインの情報が合格した / 不合格だった割合）を記録して、Tier の一覧の見直しに使う。

### 6.4 網羅表

調査の進み具合は、LLM の記憶ではなく **表** で管理する。

| 観点 | 出典数 | 主な出典 | 食い違い | 状態 |
|---|---|---|---|---|
| 建設年 | 2 | 自治体ページ、郷土史 | なし | 確認済み |
| 現状 | 1 | 個人ブログ | — | 出典不足 |
| 外観の特徴 | 0 | — | — | 未発見 |
| 画像 | 合格 0 枚 / 候補 12 件 | — | — | 未発見 |

- ⑨ の不足判定は、まずこの表の穴（出典 0〜1 件、合格画像 0 枚）をプログラムが列挙する。

### 6.5 足切り（深掘りする前のふるい分け）

深掘り（LLM）の回数を減らすため、プログラムが簡単な基準で候補を絞る。

| 基準 | 内容 |
|---|---|
| 重複 | 同じ URL・同じ画像（同じファイル名・ほぼ同じサイズ）を 1 つにまとめる |
| 名前の有無 | タイトル・URL・要約に、対象の名前（別名・型番を含む）が入っているか |
| 情報源の Tier | 6.3 の Tier で並べる（Tier 1 が先）。Tier 5 は深掘りしない |
| 除外語 | 除外語を含む候補を外す |

- 足切りは「捨てる」ではなく **深掘りする順番を決める** ために使う。上位から深掘りし、上限（11 章）に達したら残りは記録だけ残す。

### 6.6 検索の道具の使い分け（SearXNG の位置づけ）

SearXNG は **候補を広く集める入り口** として使う。取れるのは検索結果の一覧と短い要約までで、
ページの本文は取れない。また Wikipedia / Wikidata などを SearXNG 経由で個別に検索すると不安定だった
（2026-10-28 の確認結果。13 章 U-10）。そのため、道具を次のように使い分ける。

| 目的 | 使う道具 | 取れる情報 | Tier |
|---|---|---|---|
| 文章の候補を広く集める | SearXNG 一般検索 | タイトル・URL・要約（平均約 100 文字）・返したエンジン・一部に公開日。1 回 40 件前後 | 結果のドメインで分類 |
| 対象の概要・同名候補の手がかり | SearXNG の infobox / answers | Wikipedia・Wikidata 由来の概要・代表画像・属性・関連リンク | 2 |
| 検索の言葉を広げる | SearXNG の suggestions | 関連する検索の言葉（例:「水星 表面」「水星 温度」） | — |
| 学術の出典 | SearXNG 学術カテゴリ（`categories=science`） | 著者・雑誌名・DOI・出版日・PDF の URL・要約（arXiv, PubMed, Semantic Scholar, Crossref など） | 1 |
| 画像の候補を広く集める | SearXNG 画像カテゴリ（`categories=images`） | 画像 URL・掲載ページ URL・タイトル・解像度・サムネイル | 掲載ページのドメインで分類 |
| Wikipedia / Wikidata / Commons | **公式 API を直接呼ぶ**（SearXNG 経由にしない） | 本文・別名・代表画像・ライセンス・曖昧さ回避 | 2 |
| 分野別データベース | **各データベースの API を直接呼ぶ** | データベースごとに異なる | 1〜2 |
| ページ本文・ページ内の画像 | `fetch_page`（ページを取得して HTML を解析） | 本文全体、画像とキャプション・alt・周りの文章 | — |

#### SearXNG を使うときのルール

| # | ルール | 理由（確認結果） |
|---|---|---|
| G-1 | 判断はページ本体で行う。要約（`content`）だけで事実を採用しない | 要約は約 100 文字で、文脈が切れている |
| G-2 | 特定のデータベースだけを狙うときは、SearXNG のエンジン指定（`engines=`）に頼らず、API を直接呼ぶ | `categories=` と一緒に指定すると、カテゴリ内の全エンジンが動いた |
| G-3 | 画像検索の `site:` 指定に頼らず、掲載ページの URL のドメインをプログラムで確かめて Tier を付ける | 画像検索に `site:go.jp` を付けても Wikimedia の画像が返った |
| G-4 | 検索と検索の間隔をあけ、同時に送る検索の数を制限する | 続けて検索すると Bing・Brave・Google の画像検索がタイムアウトし、DuckDuckGo の画像検索は「アクセス拒否」で一時停止された |
| G-5 | 応答しなかったエンジン（`unresponsive_engines`）を `attempts_log` に記録し、時間をおいて 1 回だけやり直す | 一時的な失敗で「見つからなかった」と判断しないため |
| G-6 | 応答しなかったエンジンがある状態で「見つからなかった」と報告するときは、そのことも申告する（9.2） | 調べ尽くしていないのに、調べ尽くしたように見せないため |
| G-7 | suggestions は検索の言葉の候補（`query_pool`）に加えるが、対象を特定する言葉と合わないものは使わない | 「水星 歌詞」のように別の対象（曲名）が混ざる |

## 7. ⑥⑦ 縦の調査: LLM による深掘り

### 7.1 深掘りタスクの単位

| 種類 | 1 タスクの中身 |
|---|---|
| 文章 | 1 つの観点 × 1 つのページ（例:「旧□□小学校の建設年」×「自治体の沿革ページ」） |
| 参照の追跡 | 1 つの事実 × その事実の参照先 1 つ |
| 画像 | 1 つの画像候補（画像 + 掲載ページ + 見分ける特徴） |

### 7.2 文章の深掘りの手順

1. ページ本体を取得する（プログラム）。検索結果の要約だけで判断しない
2. LLM が、その観点について書かれた部分を精読し、事実を **原文の引用付き** で抜き出す（M-4）
3. 同時に、別名・旧称・型番など **新しい検索の言葉** と、**見分ける特徴** があれば抜き出す
4. ページが別の資料を参照している場合（出典欄、リンク）、その参照先を次の深掘りタスクにする（縦の再帰。深さは 2 段まで）
5. プログラムが引用をページ本文と照合する（⑦）。一致しない事実は捨てる

### 7.3 出力の形（例）

```json
{
  "aspect": "建設年",
  "facts": [
    {"claim": "1932 年に木造校舎が建設された", "quote": "昭和七年、木造二階建ての校舎が完成", "confidence": "high"}
  ],
  "new_terms": ["△△村立□□尋常小学校"],
  "distinguishing_features": ["木造二階建て", "正面に時計台"],
  "references_to_follow": ["https://example.com/kyodoshi.pdf"],
  "not_found": false
}
```

### 7.4 文章の正確さのルール

| # | 要件 |
|---|---|
| T-1 | 主要な事実は、6.3 の「確認済み」の基準（独立した 2 出典以上、うち 1 つ以上が Tier 1〜2 など）で確かめる（出典数・Tier はプログラムが数える） |
| T-2 | 出典が 1 つしかない事実は「出典 1 件のみ」と明記する |
| T-3 | 出典どうしで食い違う場合は、両方を併記して食い違いを報告する（どちらかを勝手に選ばない） |
| T-4 | 出典の信頼度は 6.3 の Tier で区別する。報告の出典一覧にも Tier を付ける。Tier 5 は出典にしない |
| T-5 | 引用がページに実在しない事実は使わない（M-4） |

## 8. 画像: 横で集めて、縦で確かめる

### 8.1 探索（横・プログラム）

次の段階を **すべて** プログラムが実行し、候補を集める（LLM に「次はどこを探すか」を選ばせない）。

| 段階 | 方法 | 向いている対象 | 備考 |
|---|---|---|---|
| L1 | **画像検索（SearXNG の画像カテゴリ）**。6.2 の組み合わせで複数回検索 | 有名な対象 | 画像 URL と掲載ページが取れることは確認済み（U-1）。`site:` は効かないため、Tier は掲載ページの URL で付ける（G-3） |
| L2 | **Wikipedia / Wikidata の代表画像、Wikimedia Commons の検索 API** | 百科事典に載る程度の対象 | ライセンスが明記されている。SearXNG 経由ではなく公式 API を直接呼ぶ（G-2） |
| L3 | **分野別のデータベース**: 生物（iNaturalist、GBIF）、文化財・歴史（国立国会図書館デジタルコレクション、文化遺産オンライン）、製品（メーカー公式）など | マイナーだが専門の記録がある対象 | 分野ごとにツールを用意する |
| L4 | **文章の深掘りで使ったページ内の画像**: キャプション・alt 属性・周りの文章と一緒に取り出す | 画像検索には出ないが、記事には載っている対象 | 例 B に有効 |
| L5 | **周辺の画像**: 所在地・上位の分類・関連する出来事で探す | 単独の写真がない対象 | 「対象そのものではない」と明記して出す |

- 集めた候補は 6.5 の足切りで深掘りの順番を決める。
- **画像を生成して代用することはしない。**

### 8.2 検証（縦・LLM、1 候補ずつ）

マイナーな対象では、VLM（画像を読める LLM）に「これは〇〇か？」と聞いても正しく判定できない。
そのため、1 候補ずつ、掲載ページの文脈と見分ける特徴を渡して深く照合する。

| # | チェック | 担当 | 重み |
|---|---|---|---|
| V-1 | 掲載ページの文脈: キャプション・alt・周りの文章に、対象の名前があり、その画像が対象を指していると読めるか | LLM（ページを精読） | 高 |
| V-2 | 掲載ページの Tier（6.3。ページ単位の調整を含む） | プログラム（Tier の一覧）+ LLM（調整） | 高 |
| V-3 | 特徴の一致: 画像に、見分ける特徴（7.2 で収集）が写っているか、矛盾する特徴がないか | LLM（VLM） | 中 |
| V-4 | 複数の出典での一致: 別の出典に同じ画像・同じ対象の画像があるか | プログラム（画像の重複判定）+ LLM | 中 |
| V-5 | 画像として使えるか（アクセスできる、解像度、対象がはっきり写っている） | プログラム + LLM | 必須 |
| V-6 | ライセンス | プログラム（取得できる場合） | 情報として付ける |

### 8.3 判定

| 判定 | 条件（目安） | 出し方 |
|---|---|---|
| **確認済み** | V-5 を満たし、V-1 が高く、掲載ページが Tier 1〜2（V-2）、V-3 で矛盾がない | そのまま出す（出典付き） |
| **おそらく正しい** | V-5 を満たし、V-3 で矛盾がなく、「V-1 は高いが掲載ページが Tier 3〜4」または「Tier 1〜2 だが V-1 が中程度」 | 「確認しきれていない」と添えて出す |
| **参考画像** | 対象そのものではないが関連する（L5 の周辺の画像、兄弟機種など） | 「〇〇そのものではない」と明記して出す |
| **不採用** | V-5 を満たさない、または V-3 で明らかな矛盾がある | 出さない。不合格の理由を記録する（10 章 R-4） |

- 判定の目安は、例 A〜D と 12 章のテストで調整する。

## 9. ⑩⑪ 報告と正直な申告

### 9.1 報告の形

```
## 〇〇について

（前提: 〜と解釈して調査しました）           ← 質問で決めきれなかった前提がある場合

### 概要
（本文。主要な事実には [1] [2] のように出典番号を付ける）

### 画像
![説明](画像URL)
- 出典: 〇〇（掲載ページの URL）　ライセンス: 〇〇
- 確信度: 確認済み / おそらく正しい / 参考画像（〇〇そのものではない）

### 確認できなかったこと
- 〜（出典が見つからなかった / 出典どうしで食い違いがあった）

### 出典
[1] タイトル — URL
[2] ...
```

- 報告を書く LLM には、プログラムが網羅表と合格した事実・画像だけを渡す（M-5）。
  出典番号の対応づけと「確認できなかったこと」の一覧は、プログラムが網羅表から作る。

### 9.2 見つからなかったときの申告

画像（または情報）が見つからなかったときは、次の 4 点を必ず書く。
「試した方法」は LLM の記憶ではなく、プログラムの記録（`attempts_log`）から作る。

1. **何が見つからなかったか**
2. **試した方法**（例: 「画像検索を 8 通りの言葉で、Wikimedia Commons、〇〇データベース、調査で使った 5 ページを確認。候補 23 件を検証し、合格 0 件。3 巡の再調査でも新しい手がかりなし」）
3. **見つからなかった理由の見立て**（例: 「公開されている写真がない可能性が高い」「同名の別の学校の写真しか見つからなかった」）
4. **次にできること**（例: 「郷土資料館への問い合わせ」「お持ちの画像があれば、それが対象かを確認できます」）

### 9.3 してはいけないこと

| # | 禁止事項 |
|---|---|
| X-1 | 検証していない画像を、対象の画像として出す |
| X-2 | 似たもの・別のものの画像を、それと明記せずに出す |
| X-3 | 画像を生成して、実物の画像の代わりに出す |
| X-4 | 出典のない事実、引用を照合できなかった事実を、確かな事実のように書く |
| X-5 | 「見つからなかった」ことを隠して、関係の薄い情報で埋める |

## 10. 再帰による精度向上

調べた結果から次に調べることを決め、同じ手順を繰り返す。再帰も **横（プログラム）** と **縦（LLM）** に分ける。

### 10.1 横の再帰（プログラムが駆動）

| # | 再帰 | きっかけ | 何をするか |
|---|---|---|---|
| R-1 | **観点の追加** | 網羅表に穴がある（出典 0〜1 件の観点） | その観点について、未実行の検索の言葉・情報源で ⑤ を再実行 |
| R-3 | **言葉の展開** | 深掘りで新しい別名・旧称・型番が見つかった | 6.2 のテンプレートに加えて、⑤ を再実行（例 B: 旧称で検索し直す） |
| R-4 | **除外語の追加** | 画像・ページが別物と判定された | 除外語に加えて、⑤ を再実行（例 C: 兄弟機種を除外） |

### 10.2 縦の再帰（LLM が深掘り）

| # | 再帰 | きっかけ | 何をするか |
|---|---|---|---|
| R-2 | **参照の追跡** | ページが別の資料を参照している | 参照先を読み、一次資料で事実を確かめる（深さ 2 段まで） |
| R-6 | **1 件の確かめ直し** | 事実の根拠が弱い、出典どうしが食い違う | その事実だけを対象に、より信頼度の高い情報源を深掘りする |
| R-5 | **新しい曖昧さ → 利用者に質問** | 深掘り中に、同名の別の対象が見つかった | ③ に戻って確認する（例: 同じ名前の学校が 2 つの村にあった） |

### 10.3 止めるための条件

| # | 条件 | 既定値（案） |
|---|---|---|
| S-1 | 網羅表に穴がなくなった | — |
| S-2 | 再調査の巡回数が上限に達した | 3 巡 |
| S-3 | 参照の追跡の深さが上限に達した | 2 段 |
| S-4 | 直前の巡回で新しい情報（新しい事実・新しい合格画像・新しい言葉）が 1 つも出なかった（**収束**） | — |
| S-5 | 検索回数・深掘り回数・時間の上限に達した | 検索 30 回 / 深掘り 40 件 / 15 分（U-6） |
| S-6 | 利用者への質問が上限に達している状態で、新しい曖昧さが見つかった | 前提を明示して進める |

- 止めるかどうかの判定は、プログラムが状態の数値（巡回数・深さ・残り回数・新しい情報の数）で行う。LLM に「もう十分か」を判断させない。
- 上限で止まった場合は、網羅表に残った穴を 9.2 の形で **正直に申告** する。
- 同じ検索の言葉・同じページ・同じ画像を 2 回深掘りしないよう、すべて `attempts_log` に記録する。

### 10.4 再帰しても変えないこと

- 検証の基準（8 章）は、巡回を重ねても **緩めない**。巡回数が増えたからといって「おそらく正しい」を「確認済み」に格上げしない。
- 見つからなかった場合に、関係の薄い情報で埋めない（X-5）。再帰の目的は精度を上げることで、量を増やすことではない。

## 11. LangGraph への対応づけ（実装の見通し）

### 11.1 ノード

| ノード | 4 章の段階 | 担当 | 処理 |
|---|---|---|---|
| `analyze_request` | ① | LLM | 依頼を項目に分解し、対象の種類を判定 |
| `check_ambiguity` | ② | プログラム + LLM | 同名候補をプログラムが検索し、LLM が不明点を判定 |
| `ask_user` | ③ | — | 質問を出して利用者の回答を待つ（`interrupt` で一時停止） |
| `check_feasibility` | ④ | LLM | 公開情報で調べられる依頼か判定 |
| `expand_breadth` | ⑤ | プログラム | 観点 × 言葉を展開し、埋まっていない観点について **次の Tier** を検索（6.3）。重複除去・足切りをして、深掘りタスクのキューを作る |
| `deep_dive_text` | ⑥ | LLM | 1 タスク（1 観点 × 1 ページ）を深掘り。引用・新しい言葉・特徴・参照先を出力 |
| `deep_dive_image` | ⑥ | LLM | 1 画像候補を検証（V-1, V-3, V-5） |
| `check_quotes` | ⑦ | プログラム | 引用がページに実在するかを照合 |
| `aggregate` | ⑧ | プログラム | 網羅表の更新、出典数の集計、食い違いの検出、画像の判定（8.3） |
| `find_gaps` | ⑨ | プログラム + LLM | 網羅表の穴を列挙（プログラム）、穴 1 件ずつ次の行動を判断（LLM） |
| `compose_report` | ⑩ | LLM | 絞り込んだ材料から報告を作成 |

### 11.2 横と縦の実現方法

| 仕組み | LangGraph での実現 |
|---|---|
| 深掘りの並行実行 | `expand_breadth` が作ったキューを、`Send` でタスクの数だけ `deep_dive_text` / `deep_dive_image` に振り分ける（map） |
| 集約 | `aggregate` はプログラムのノード。各深掘りの JSON 出力を状態のリストに追加し（reducer）、網羅表を作り直す（reduce） |
| 横の再帰（R-1, R-3, R-4） | `find_gaps` → `expand_breadth` の条件付きエッジ |
| 縦の再帰（R-2, R-6） | `find_gaps` → 深掘りタスクを直接キューに追加して `Send` |
| R-5 | `find_gaps` → `ask_user` の条件付きエッジ |
| 止める条件 | `find_gaps` の後の条件付きエッジで、状態の数値（10.3）を判定。念のため `recursion_limit` も設定する |

### 11.3 状態（State）に持たせる情報

| 項目 | 内容 |
|---|---|
| `request` | 利用者の依頼（原文） |
| `spec` | 分解した項目（対象・対象の種類・目的・範囲・画像の要件・出力の形） |
| `assumptions` | 質問で決めきれず、置いた前提 |
| `questions_asked` | 質問した回数（最大 2 往復の管理） |
| `aspects` | 観点チェックリストから展開した観点の一覧 |
| `query_pool` | 検索の言葉の集まり（新しい言葉が追加される。R-3） |
| `excluded_terms` | 除外語（R-4） |
| `task_queue` | 深掘りタスクのキュー（種類・対象・優先度） |
| `findings` | 深掘りの出力（7.3 の JSON）のリスト |
| `coverage` | 網羅表（6.4）。観点ごとに、調べ終えた Tier と状態（確認済み / 出典不足 / 未発見）を持つ |
| `source_tiers` | Tier の一覧（設定ファイルから読み込む）と、ページ単位の調整結果 |
| `image_candidates` | 画像候補（URL・掲載ページ・キャプション・段階・足切りの点数・検証結果） |
| `attempts_log` | 試したことの記録（検索の言葉・情報源・ページ・画像。9.2 の申告と重複防止に使う） |
| `round` / `budget` | 巡回数・残りの検索回数と深掘り回数と時間（10.3） |
| `new_info_count` | 直前の巡回で増えた情報の数（S-4 の収束判定） |
| `report` | 最終報告 |

## 12. 評価方法

実装後、次のテストケースで動きを確かめる。

| # | 種類 | 期待する動き | 合否の基準 |
|---|---|---|---|
| E-1 | 同名の対象（例 A） | 調査前に質問する | 質問せずに調査を始めたら不合格 |
| E-2 | 明確な依頼 | 質問せずに調査する | 不要な質問をしたら不合格 |
| E-3 | 有名な対象 | 確認済みの画像を出す | 画像が対象と一致 |
| E-4 | マイナーな対象（例 B） | L1〜L5 をすべて試す。見つからなければ申告 | 別物の画像を「確認済み」で出したら不合格 |
| E-5 | 似たものが多い対象（例 C） | 見分ける特徴で照合し、不確かなら明記 | 兄弟機種の画像を断定して出したら不合格 |
| E-6 | 実現不可能な依頼（例 D） | 早い段階で申告 | 探し回った末にでたらめな結果を出したら不合格 |
| E-7 | 出典どうしで食い違いがある対象 | 両方を併記 | 一方だけを事実として書いたら不合格 |
| E-8 | 別名・旧称でしか見つからない対象 | R-3 で見つけた言葉で検索し直して見つける | 最初の言葉だけで諦めたら不合格 |
| E-9 | 調査中に同名の別対象が判明する対象 | R-5 で利用者に確認する | 確認せずに混ぜて報告したら不合格 |
| E-10 | どれだけ調べても情報が増えない対象 | 10.3 の条件で止まり、残った穴を申告する | 止まらない、または穴を申告しなかったら不合格 |
| E-11 | 観点の多い対象 | 観点チェックリストの全観点について、調べた結果（見つかった / 見つからなかった）を報告する | 観点を黙って抜かしたら不合格 |
| E-12 | 作り話を誘いやすい対象 | 引用を照合できない事実を報告に含めない | 照合できなかった事実を書いたら不合格 |
| E-13 | 公的機関・百科事典に情報がある対象 | Tier 1〜2 で観点が埋まり、Tier 3 以下を検索しない | 埋まった後も下の Tier を検索したら不合格 |
| E-14 | 個人サイトにしか情報がない対象 | Tier 3〜4 まで降りて見つけ、「出典不足」または「おそらく正しい」として出す | 見つけられない、または「確認済み」として出したら不合格 |
| E-15 | Pinterest・まとめサイトに画像が多い対象 | Tier 5 を出典にせず、元の掲載ページを探す | Tier 5 のページを出典として出したら不合格 |
| E-16 | 検索エンジンが一部応答しない状況 | 記録してやり直し、それでも応答しなければ報告で申告する | 応答しなかったことを申告せずに「見つからなかった」と報告したら不合格 |

- 評価のための正解データ（対象・正しい画像の URL）は別途用意する。
- 最も重視する指標は **「誤った画像を確認済みとして出した数」= 0**。見つからなかった数より優先する。
- 比較実験: 同じテストケースを次の 3 通りで実行し、本設計の効果を確かめる。
  1. LLM 単体（1 回の検索結果をまとめるだけ）
  2. 横も縦も LLM に任せた再帰
  3. 本設計（横はプログラム、縦は LLM）

  比べる指標: 正しい画像を見つけた数、観点の取りこぼし数、出典 2 件以上の事実の割合、引用照合で捨てた事実の数、検索回数、所要時間。

## 13. 未決事項

| # | 内容 | 案 |
|---|---|---|
| U-1 | SearXNG の画像検索で、画像 URL と掲載ページの URL が取れるか | **確認済み（2026-10-28）**: `categories=images` で `img_src`（画像）・`url`（掲載ページ）・`title`・`resolution`・`engine` が取れる。エンジンは Bing / Brave / Google CSE / Pinterest。Pinterest は掲載ページが元の出典でないことが多いため、Tier 5 とする |
| U-2 | 分野別データベース（L3）と観点チェックリストを、どの分野から用意するか | 研究室で調査を頼みそうな分野を挙げて、1〜2 分野から始める |
| U-3 | 画像のライセンスの扱い | v1 は「表示するだけ」とし、ライセンスは情報として付ける。資料への転載は利用者の判断とする |
| U-4 | Open WebUI での画像の表示方法 | Markdown の画像記法（`![](URL)`）で表示できるかを確認する |

| U-6 | 調査の時間・検索回数・深掘り回数・再帰の上限 | 10.3 の既定値から始め、共有サーバーの負荷と E-10 の結果を見て調整する。深掘りは並行で行うため、同時実行数は研究室サーバーの同時処理数（4）以下にする |
| U-7 | 不足判定（`find_gaps`）の LLM を報告役と同じモデルにするか | v1 は同じ qwen3.8-27b で、指示（プロンプト）を分けて別の役にする |
