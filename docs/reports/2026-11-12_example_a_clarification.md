# 実装レポート: 例 A「同名の対象を聞き返す」

- 日付: 2026-11-12
- ブランチ: `feature/example-a-clarify`
- 対象の設計: [task_flow_design.md](../task_flow_design.md) の例 A、5 章（不明点の判定と質問）
- 位置づけ: 実装計画（[implementation_plan.md](../implementation_plan.md)）のフェーズ 0〜2 の一部を、例 A に絞って縦に通したもの

## 1. 目的

例 A の 3 つのフェーズが動くこと。

| フェーズ | 行動 | 状態 |
|---|---|---|
| 1 | 調べる（起動するかはエージェントが選ぶ） | わかったこと: 水星・水銀・企業など複数の意味がある / わからないこと: 利用者がどれを聞いているか |
| 2 | 聞き返す（理想）。**適当な対象で答える・全部を平たく述べる（悪い例）はしない** | 利用者の回答で対象が決まる |
| 3 | 応答（調査内容の提示） | — |

## 2. 作ったもの

### 2.1 構成

```
START → decide ─┬→ search ───→ decide
                ├→ ask_user ─→ decide   （interrupt で一時停止して回答を待つ）
                └→ respond ──→ END
```

| ファイル | 役割 |
|---|---|
| `src/my_llm_app/agent/graph.py` | LangGraph のグラフ |
| `src/my_llm_app/agent/nodes.py` | 各ノード（decide / search / ask_user / respond） |
| `src/my_llm_app/agent/guard.py` | LLM が選んだ行動をプログラムで検査する |
| `src/my_llm_app/agent/prompts.py` | 各ノードの指示とスキーマ |
| `src/my_llm_app/agent/state.py` | 状態と上限値 |
| `src/my_llm_app/tools/wikimedia.py` | Wikidata / Wikipedia の公式 API |
| `src/my_llm_app/tools/searxng.py` | SearXNG による Web 検索 |
| `src/my_llm_app/llm.py` | LLM の呼び出し（JSON スキーマ、接続エラー時のやり直し、時間の記録） |
| `scripts/agent.py` | CLI（`-v` で各ノードの状態を表示、`runs/` に実行記録） |
| `tests/` | 単体テスト 20 個（LLM・外部 API なしで実行） |

### 2.2 設計書の方針との対応

| 方針（設計書） | 実装 |
|---|---|
| 横はプログラム、縦は LLM（3 章） | 行動の選択は LLM、その検査（上限・繰り返し・曖昧なままの応答）はプログラム。候補の並べ替え・有名さの判定・番号の対応づけ・出典番号の割り当てもプログラム |
| LLM の出力は JSON（M-3） | 行動の選択・状態の更新・回答の照合は JSON スキーマで出力させる |
| 作り話の防止（M-4 の簡易版） | LLM には候補の **ID を選ばせるだけ**にし、名前・説明は Wikidata の実データで埋める。事実の根拠 URL は、実際に取得した検索結果のものだけを認める |
| 質問は選択肢付き・まとめて 1 回（Q-1, Q-2） | 質問文はプログラムが候補一覧から作る（最大 8 択） |
| 調べればわかることは聞かない（Q-3） | 何も調べていない段階の「聞き返す」は「調べる」に切り替える |
| 質問は最大 2 往復（Q-4） | 上限に達したら前提を明示して応答 |
| おまかせの前提は報告に書く（Q-5） | 利用者に確かめずに対象を決めた場合は、冒頭に前提を書く |

### 2.3 プログラムによる検査（guard）

| 条件 | 処理 |
|---|---|
| 対象が決まっていない（候補 2 つ以上）のに「応答」を選んだ | 「聞き返す」に切り替える（**例 A の悪い例を止める**） |
| まだ何も調べていないのに「聞き返す」を選んだ | 「調べる」に切り替える |
| 対象が決まったのに、その対象をまだ調べていない | 応答の前に対象を調べる |
| 直前と同じ質問をしようとした | 前提を明示して応答する |
| 同じ検索の繰り返し、行動の上限（8 回）、質問の上限（2 回） | 繰り返しを止める / 応答に切り替える |

## 3. テストの方法

- 単体テスト: `uv run pytest`（20 個。LLM と外部 API は偽物に差し替え）
- 実際の LLM（qwen3.8-27b）と検索を使い、同名の対象 6 件を自動応答で実行した

| # | 依頼 | 自動で返した回答 | 期待する動き |
|---|---|---|---|
| 1 | マーキュリーについて調べて | 水星についてです | 聞き返す → 水星 |
| 2 | アマゾンについて調べて | 川のほうです | 聞き返す → アマゾン川（選択肢にない回答） |
| 3 | ジャガーについて調べて | 動物です | 聞き返す → 動物のジャガー |
| 4 | Pythonについて調べて | プログラミング言語 | 聞き返す → プログラミング言語 |
| 5 | スマトラ島沖地震について調べて | 2004年の地震 | 聞き返す → 2004 年の地震 |
| 6 | 富士山について調べて | （聞かれたら「山です」） | 聞き返さずに答えるのが理想 |

## 4. 結果

### 4.1 最終結果（全件合格）

| # | 動き | 出典 [1] | 出典のない事実 | 時間 |
|---|---|---|---|---|
| 1 | 8 択で聞き返す → 水星に特定 → 回答 | Wikipedia: 水星 | 0 | 4.3 分 |
| 2 | 8 択で聞き返す → 選択肢にない「川」→ 次の検索でアマゾン川を特定 → 回答 | Wikipedia | 0 | 4.9 分 |
| 3 | 8 択で聞き返す → 動物のジャガーに特定 → 回答 | Wikipedia | 0 | 4.7 分 |
| 4 | 8 択で聞き返す → 回答直後に特定 → 対象を調べて回答 | Wikipedia: Python | 0 | 3.4 分 |
| 5 | 8 択（2000〜2012 年の地震）で聞き返す → 2004 年に特定 → 回答 | Wikipedia: スマトラ島沖地震 (2004年) | 0 | 5.7 分 |
| 6 | **聞き返さない**。冒頭に「一般に静岡・山梨の富士山を指すため、それとして調べました。別のもの（軍艦、群馬県の山 など）であれば教えてください」 | Wikipedia: 富士山 | 0 | 2.3 分 |

- 明確な依頼（「太陽系の惑星の水星について調べて」）では聞き返さずに答えることも確認した。
- 番号での回答（「2」）が、表示した選択肢の 2 番に正しく対応することも確認した。

### 4.2 途中で見つかった問題と対策

実行記録（`runs/`）を読んで見つけた問題と、その対策。

| # | 見つかった問題 | 原因 | 対策 |
|---|---|---|---|
| 1 | 「マーキュリー」の候補に水星が出ない | 日本語の Wikidata では水星は「水星」で登録されている | 英語名でも検索する（LLM が `names` に原語を入れる） |
| 2 | 出典 [1] が「Wikipedia: パスタ」になった | LLM が水星の ID を `Q178`（パスタ）と書き間違えた | LLM には ID を選ばせるだけにし、名前と説明は Wikidata の実データで埋める。取得していない ID は認めない |
| 3 | 「1」と答えたら別の選択肢として扱われた | LLM には番号付きの選択肢が見えない | 番号での回答はプログラムが対応づける |
| 4 | 回答のすべての事実の出典が [1] | 事実と出典の対応を持っていなかった | 事実ごとに根拠 URL を持たせ、出典番号はプログラムが割り当てる |
| 5 | 対象が決まった後も、他の意味の説明が回答に残る | 状態の更新で古い事実を残していた | 対象が決まったら、その対象の事実だけを残す |
| 6 | 選択肢の 8 番が空欄 | 名前のない Wikidata の項目 | 名前のない候補を外し、有名な順（sitelinks の多い順）に並べる |
| 7 | はっきり答えても対象が決まらず、同じ質問を繰り返す（Python・地震） | 対象を決める処理が「調べる」の中にしかなく、回答後に LLM が直接「応答」を選ぶと決まらない | 回答の直後に、回答と選択肢を照合して対象を決める |
| 8 | 「山です」で対象が決まらず、同じ質問を繰り返す（富士山） | 回答に合う候補が複数あった | 候補を絞って聞き直す。同じ質問はしない |
| 9 | 富士山で聞き返してしまう | 有名な意味が 1 つしかない場合を区別していなかった | sitelinks の 1 位が 2 位の 4 倍以上なら、聞き返さずに前提を明示して進める |
| 10 | LLM サーバーに一時的につながらず止まる | やり直しがない | 10 秒・30 秒・60 秒待ってやり直す |
| 11 | 1 件に最大 16 分かかる | 状態の更新の出力が長い、同じ質問の繰り返し | 出力を短くする（事実は最大 8 件・60 文字以内）。繰り返しの解消と合わせて 2〜6 分に短縮 |

### 4.3 有名さの判定のしきい値

候補が何言語版の Wikipedia に記事を持つか（sitelinks）を比べた。

| 依頼 | 1 位 | 2 位 | 比 | 判定 |
|---|---|---|---|---|
| マーキュリー | 水星 274 | 水銀 187 | 1.5 | 聞き返す |
| Python | Python 164 | ニシキヘビ科 79 | 2.1 | 聞き返す |
| スマトラ島沖地震 | 2004 年 87 | 32 | 2.7 | 聞き返す |
| 富士山 | 静岡・山梨の山 146 | 群馬県の山 8 | 18 | **聞き返さない** |

しきい値は 4 倍とした（`DOMINANCE_RATIO`）。生の検索結果には前方一致の無関係な項目（ジャカルタ、ジャガイモなど）が混ざるため、比較は LLM が選んだ候補の中だけで行う。

## 5. 残っている課題

| # | 課題 | 例 | 対応の予定 |
|---|---|---|---|
| 1 | 事実を検索結果の要約（約 100 文字）から取っている。ページ本文を読んでいない | スマトラ島沖地震で、現地時間の「7 時 58 分」を日本時間として書いた（出典どうしの食い違いには気づいて注記はしている） | 実装計画フェーズ 1（ページ本文の深掘り・引用の照合）とフェーズ 3（食い違いの検出） |
| 2 | 1 件 2〜6 分かかる | 共有サーバーの混み具合で変わる | 実行記録の LLM 呼び出し時間を見て、遅い処理を特定する |
| 3 | 有名さのしきい値（4 倍）は 6 件で決めただけ | — | テストケースを増やして調整する |
| 4 | Web 検索だけで見つかる候補（Wikidata にない意味）は選択肢に出ない | — | 必要になれば対応 |
| 5 | テストケースの自動実行は作業用のスクリプトで行った | — | 実装計画の `scripts/eval.py` としてリポジトリに入れる |

## 6. 試し方

```sh
docker compose up -d                       # SearXNG（開発用に 127.0.0.1:8888 を公開）
uv sync
uv run scripts/agent.py "マーキュリーについて調べて" -v
uv run pytest
```

`.env` に `SEARXNG_URL=http://localhost:8888` が必要（`.env.example` 参照）。

## 7. レビューで見てほしい点

- guard の検査（2.3）で、止めすぎ・止め足りないケースがないか
- 有名さで聞き返しを省く判断（しきい値 4 倍）が妥当か。省いた場合の前提の書き方
- プロンプト（`prompts.py`）の指示の曖昧さ
- 実行記録を 1〜2 件読んで、おかしな動きがないか（`uv run scripts/agent.py ... -v` で再現できる）
