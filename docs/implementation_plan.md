# 実装計画: 調査エージェント

- 作成日: 2026-11-11
- 状態: ドラフト（レビュー待ち）
- 対象の設計: [task_flow_design.md](task_flow_design.md)（以下「設計書」）
- 方針: **最小構成で端から端まで動かし、フェーズごとに少しずつ大きくする。** 各フェーズの終わりに必ずデバッグとレビューを行い、合格してから次へ進む。
- テレメトリー（可視化）は保留。各フェーズのデバッグは、実行記録のファイルと CLI の表示で行う（0.3）。

## 0. 全フェーズ共通の進め方

### 0.1 フェーズの流れ

```
計画の確認 → 実装 → 自分でデバッグ → テストケースで確認 → レビュー（PR） → 修正 → main に取り込み → 次のフェーズ
```

- 1 フェーズ = 1 つのブランチ（例: `phase-1-minimal-loop`）と 1 つの PR。
- `main` には直接 push しない。PR でレビューを受けてから取り込む。

### 0.2 各フェーズの「完了の条件」の書き方

各フェーズに次の 4 つを決めておく。

| 項目 | 内容 |
|---|---|
| ゴール | このフェーズで動くようになること（1〜2 文） |
| やること | 実装する部品（設計書のどの節に当たるか） |
| デバッグ | 何を見て、どう確かめるか |
| レビューの合格条件 | テストケースの結果と、レビューで確認する観点 |

### 0.3 デバッグの共通の仕組み（フェーズ 0 で作る）

| 仕組み | 内容 |
|---|---|
| CLI での実行 | `uv run scripts/agent.py "依頼文"` で 1 回実行。`--verbose` で、ノードを通るたびに名前と状態の要約を表示する |
| 実行記録 | 1 回の実行ごとに `runs/<日時>/` に保存する（git 管理外）。中身: 各ノードの入力と出力、LLM へのプロンプトと応答、検索・API の呼び出しと結果、最終報告 |
| 記録の再生 | 保存した検索結果・ページを使って同じ実行を再現できるようにする（`--replay runs/<日時>`）。LLM のプロンプトだけを変えて比べられる。共有サーバーと検索エンジンへの負荷も減る |
| 単体テスト | `uv run pytest`。LLM と外部 API は偽物（モック）に差し替え、プログラムの部分（集計、Tier の判定、引用の照合など）を確かめる |
| テストケース | 設計書 12 章の E-1〜E-16 を `tests/cases/*.yaml` に書く（依頼文・期待する動き・正解）。`uv run scripts/eval.py` で、実際の LLM を使ってまとめて実行し、合否を表にする |

### 0.4 レビューの共通の観点

どのフェーズでも、次を確認する。

| # | 観点 |
|---|---|
| RV-1 | このフェーズのテストケースがすべて合格しているか（不合格があれば理由と対応が書かれているか） |
| RV-2 | 設計書と実装が合っているか。ずれた場合は設計書を直したか |
| RV-3 | 設計書 3.3 の LLM の使い方のルール（1 回 1 件、引用必須、JSON 出力など）を守っているか |
| RV-4 | プロンプトの確認: 指示が曖昧でないか、余計な文脈を渡していないか |
| RV-5 | 実行記録を 2〜3 件読み、おかしな動き（同じ検索の繰り返し、無駄な LLM 呼び出しなど）がないか |
| RV-6 | 研究室サーバーの IP・API キーなどがコードやテストデータに入っていないか（`git grep`） |
| RV-7 | 共有サーバーへの負荷: 同時に送る数が 4 以下か、1 回の実行で LLM を何回呼んでいるか |

|---|---|---|---|
| 0 | 土台 | LangGraph が動き、LLM・検索・ページ取得の部品が単体で使える | 単体テスト |

| 4 | 画像 | 画像を集めて 1 枚ずつ検証し、確信度付きで出す | E-3, E-4, E-5, E-15 |
| 5 | 再帰 | 足りない点を見つけて調べ直し、条件で止まる | E-8, E-9, E-10, E-16 |

## 2. フェーズ 0: 土台

**ゴール**: LangGraph の空のグラフが動き、LLM・検索・ページ取得の部品を単体で呼べる。デバッグの仕組みがある。

**やること**

| 部品 | 内容 | 設計書 |
|---|---|---|
| 依存パッケージ | `langgraph`, `langchain-openai`（または `openai`）, `httpx`, HTML 解析（`selectolax` など）, `pyyaml`, `pytest` | — |
| ディレクトリ構成 | `src/my_llm_app/agent/`（グラフ・ノード）、`tools/`（検索・API・ページ取得）、`config/`（Tier 一覧・観点チェックリスト）、`tests/` | 11 章 |
| 設定の読み込み | `.env` から LLM・SearXNG の接続先を読む | — |
| LLM の呼び出し部品 | JSON で返させ、形が違ったら 1 回だけやり直す。同時実行数を 4 以下に制限 | 3.3 M-3、U-6 |
| SearXNG の呼び出し部品 | 一般・学術・画像の検索。間隔をあける、応答しなかったエンジンを記録する | 6.6 G-4, G-5 |
| ページ取得の部品 | 本文と画像（キャプション・alt・周りの文章）を取り出す。待ち時間の上限、User-Agent | 6.6、7.2 |
| デバッグの仕組み | CLI、実行記録、記録の再生、pytest の土台 | 0.3 |

**事前に必要な作業**

- SearXNG は今 Docker の中からしか使えないので、開発用にこの PC からだけ使えるポートを開ける（`127.0.0.1:8888`。要件 N-3 で認めている範囲）。
- SearXNG の設定調整（設計書 U-10）: 待ち時間を延ばす、応答しないエンジンを外す。

**デバッグ**

- 各部品を 1 つずつ実行して、結果を目で確かめる（例: 「水星」で検索して 40 件前後、ページ取得で本文が取れる）。
- 単体テストが通る。

**レビューの合格条件**

- 部品ごとの単体テストが通る。
- 実行記録が `runs/` に保存され、`.gitignore` に入っている。
- RV-6, RV-7。

## 3. フェーズ 1: 最小の調査ループ（文章のみ）

**ゴール**: 依頼を受けて、検索 → 上位のページを 1 つずつ深掘り → 引用を照合 → 出典付きの報告、が端から端まで動く。

**やること**（最小にするため、質問・観点・Tier・画像・再帰はまだ入れない）

```
analyze_request → expand_breadth（検索 1〜3 回、上位 5 ページ） → deep_dive_text（1 ページずつ、並行）
→ check_quotes → aggregate（出典数を数える） → compose_report → 終了
```

| 部品 | 内容 | 設計書 |
|---|---|---|
| `analyze_request` | 依頼から対象・範囲を取り出す（質問はまだしない） | 4 章 ① |
| `expand_breadth`（簡易版） | 依頼文から検索の言葉を作り、SearXNG で検索、重複を除いて上位 5 ページ | 4 章 ⑤ |
| `deep_dive_text` | 1 ページを精読し、引用付きの事実を JSON で返す。`Send` で並行に実行 | 7.2, 7.3 |
| `check_quotes` | 引用がページ本文に実在するかを照合し、ないものを捨てる | 3.3 M-4 |
| `aggregate`（簡易版） | 事実ごとに出典数を数える | 4 章 ⑧ |
| `compose_report` | 出典番号付きの報告。出典 1 件の事実は「出典 1 件のみ」と書く | 9.1、7.4 |

**デバッグ**

- 3 つ程度の依頼（有名な対象 1、マイナーな対象 1、出典が食い違いそうな対象 1）で実行し、実行記録を読む。
- 引用の照合で捨てられた事実の数と内容を確認する（LLM がどの程度作り話をするかの目安になる）。
- 1 回の実行での LLM 呼び出し回数と時間を記録しておく（以降のフェーズの比較の基準）。

**レビューの合格条件**

- E-12（照合できなかった事実を報告に書かない）が合格。
- 報告の事実すべてに出典番号が付いている。
- 実行記録で、各深掘りの LLM 呼び出しが 1 ページだけを扱っている（M-1）。
- RV-1〜RV-7。

## 4. フェーズ 2: 依頼の明確化

**ゴール**: 同名の対象や結果が変わる不明点があれば調査前に質問し、明確な依頼では質問しない。不可能な依頼は早めに申告する。

**やること**

| 部品 | 内容 | 設計書 |
|---|---|---|
| Wikidata / Wikipedia の API 部品 | 同名の候補を探す。**日本語と英語の両方で、別名も含めて、件数を多めに**（「マーキュリー」で惑星の水星が日本語の上位に出ない問題への対策） | 5.1、6.6 |
| `check_ambiguity` | 同名の候補と依頼を LLM に渡し、不明点を判定 | 5.1 |
| `ask_user` | 質問を出して一時停止（LangGraph の `interrupt`）。CLI では入力を待つ。最大 2 往復 | 5.2 |
| `check_feasibility` | 公開情報で調べられる依頼か判定し、不可能なら申告して終了 | 4 章 ④ |
| 前提の記録 | 決めきれなかった点を `assumptions` に入れ、報告の冒頭に書く | 5.2 Q-5 |

**デバッグ**

- 曖昧な依頼・明確な依頼・不可能な依頼をそれぞれ数件ずつ用意し、質問の有無と内容を確認する。
- 質問の文面をレビューで読み、選択肢が付いているか、聞きすぎていないかを見る。

**レビューの合格条件**

- E-1（同名で質問する）、E-2（明確なら質問しない）、E-6（不可能を早めに申告）が合格。
- 質問が 1 回にまとまっていて、最大 3〜4 問、選択肢付き（Q-1, Q-2）。

## 5. フェーズ 3: 横の網羅と Tier

**ゴール**: 観点チェックリストで調べる観点を漏れなく展開し、Tier の高い情報源から順に調べ、網羅表で進み具合を管理する。

**やること**

| 部品 | 内容 | 設計書 |
|---|---|---|
| 観点チェックリスト | `config/aspects.yaml`。**まず 1 分野（U-2 で決める）+ 汎用** | 6.1 |
| 対象の種類の判定 | `analyze_request` に追加 | 3.2 |
| 検索の言葉のテンプレート | 名前 × 観点の言葉 × 絞り込み × 除外語 | 6.2 |
| Tier の一覧 | `config/source_tiers.yaml`。ドメインの種類による仮の Tier | 6.3 |
| Tier 順の検索 | 観点ごとに Tier 1 → 4 の順。「確認済み」になったら下に降りない | 6.3 |
| 網羅表 | 観点 × 出典数・Tier・状態 | 6.4 |
| 足切りと優先順位 | 重複・名前の有無・Tier・除外語 | 6.5 |
| 転載の検出 | 文章の類似度で、ほぼ同じページを 1 つの出典として数える | 6.3 |
| Tier のページ単位の調整 | 深掘りの LLM が「1 段上げ / 下げ」を返す | 6.3 |
| 食い違いの検出 | 同じ観点で内容が違う事実を検出し、併記する | 7.4 T-3 |

**デバッグ**

- 網羅表を実行記録と CLI に表で出し、観点ごとの状態の変化を追う。
- Tier 1 で埋まった観点で、下の Tier を検索していないことを実行記録で確かめる。
- フェーズ 1 と同じ依頼で実行し、出典の質（Tier の分布）と検索回数を比べる。

**レビューの合格条件**

- E-7（食い違いの併記）、E-11（観点を黙って抜かさない）、E-13（埋まったら下の Tier に降りない）、E-14（個人サイトまで降りて見つける）が合格。
- 観点チェックリストと Tier の一覧の中身を、2 人で読んで妥当か確認する。

## 6. フェーズ 4: 画像

**ゴール**: 画像を複数の方法で集め、1 枚ずつ検証し、確信度付きで報告に載せる。見つからなければ申告する。

**やること**（まず L1, L2, L4。L3, L5 はフェーズ 6）

| 部品 | 内容 | 設計書 |
|---|---|---|
| 見分ける特徴の抽出 | 文章の深掘りの JSON に `distinguishing_features` を追加 | 7.2 |
| L1 画像検索 | SearXNG 画像カテゴリ。Tier は掲載ページの URL で付ける | 8.1、G-3 |
| L2 Wikimedia | Wikipedia / Wikidata の代表画像、Commons の API | 8.1 |
| L4 ページ内の画像 | 深掘りで使ったページから、キャプション・alt・周りの文章付きで取り出す | 8.1 |
| `deep_dive_image` | 1 候補ずつ: 掲載ページの文脈（V-1）+ VLM で特徴の照合（V-3）+ 使えるか（V-5） | 8.2 |
| 判定 | 確認済み / おそらく正しい / 参考画像 / 不採用 | 8.3 |
| 報告への追加 | 画像・出典・ライセンス・確信度。見つからない場合の申告 | 9.1、9.2 |

**デバッグ**

- 画像候補の一覧と各チェックの結果を、実行記録に表で残す。不採用の理由も残す。
- 例 B（マイナー）、例 C（似たものが多い）に近い対象で、別物の画像が「確認済み」になっていないかを 1 枚ずつ目で確認する。
- VLM の照合結果（V-3）を読み、特徴を正しく見ているかを確かめる。

**レビューの合格条件**

- E-3（有名な対象で確認済みの画像）、E-4（マイナーで申告）、E-5（似たもので断定しない）、E-15（Pinterest を出典にしない）が合格。
- **誤った画像を「確認済み」で出した数が 0**（設計書 12 章の最重要指標）。

## 7. フェーズ 5: 再帰

**ゴール**: 網羅表の穴や弱い根拠を見つけて調べ直し、止める条件で確実に止まる。止まったら残った穴を申告する。

**やること**

| 部品 | 内容 | 設計書 |
|---|---|---|
| `find_gaps` | 網羅表の穴をプログラムが列挙し、1 件ずつ LLM が次の行動を判断 | 4 章 ⑨ |
| 横の再帰 | 観点の追加（R-1）、新しい言葉の展開（R-3）、除外語（R-4） | 10.1 |
| 縦の再帰 | 参照の追跡（R-2、深さ 2 段）、1 件の確かめ直し（R-6） | 10.2 |
| 途中の質問 | 新しい曖昧さが見つかったら `ask_user` へ（R-5） | 10.2 |
| 止める条件 | 巡回数・深さ・検索回数・時間・収束（S-1〜S-6）。`recursion_limit` も設定 | 10.3 |
| 重複の防止 | `attempts_log` で同じ検索・同じページを繰り返さない | 10.3 |

**デバッグ**

- 巡回ごとに網羅表がどう変わったかを並べて表示する（どの穴が、どの再帰で埋まったか）。
- 止まった理由（どの条件か）を実行記録に残す。
- わざと情報の少ない対象で実行し、無限に回らないこと、上限で止まって申告することを確かめる。

**レビューの合格条件**

- E-8（別名で見つける）、E-9（途中で同名を発見して確認）、E-10（止まって申告）、E-16（応答しないエンジンを申告）が合格。
- フェーズ 4 までのテストケースが引き続き合格（再帰を入れて悪化していない）。
- 1 回の実行の LLM 呼び出し回数と時間が、上限（設計書 10.3）の範囲内。

## 8. フェーズ 6: 分野別データベースと堅牢化

**ゴール**: 選んだ分野の専門データベースで、マイナーな対象の画像・情報を探せる。外部サービスの失敗や制限に強くなる。

**やること**

| 部品 | 内容 | 設計書 |
|---|---|---|
| L3 分野別データベース | U-2 で決めた分野の API（例: ジャパンサーチ、国立国会図書館、iNaturalist など）。API の有無・規約・制限を設定ファイルに記録 | 8.1、6.6 |
| L5 周辺の画像 | 所在地・上位の分類で探し、「対象そのものではない」と明記 | 8.1 |
| 呼び出しの堅牢化 | User-Agent、利用制限（429）への対応、やり直し、キャッシュ | 6.6 G-4, G-5 |
| 応答しなかったことの申告 | 報告に「〇〇は応答しなかった」を入れる | 6.6 G-6 |

**デバッグ**

- フェーズ 4 で「見つからなかった」対象を、L3 を入れて再実行し、見つかるようになったか比べる。
- 外部 API をわざと失敗させて（偽物に差し替え）、記録と申告が正しいかを確かめる。

**レビューの合格条件**

- E-4 の対象で、L3 によって改善があったか（なければ理由の分析）。
- E-16 が合格。
- 各 API の利用規約を守っているか（回数、User-Agent、ライセンス表示）。

## 9. フェーズ 7: Open WebUI との接続

**ゴール**: Open WebUI からエージェントに依頼でき、質問のやり取りと進み具合の表示ができる。

**やること**

| 部品 | 内容 |
|---|---|
| OpenAI 互換の API サーバー | FastAPI で `/v1/models` と `/v1/chat/completions`（ストリーミング対応） |
| 質問のやり取り | エージェントの質問を回答として返し、次のメッセージを利用者の答えとして続きから再開する（会話ごとに状態を保存） |
| 進み具合の表示 | 網羅表・試したことの記録から、プログラムが途中経過の文を作って流す（開閉できる表示） |
| Docker への追加 | `docker-compose.yml` にエージェントのサービスを追加し、Open WebUI の接続先に加える |
| タスクモデルの設定 | Open WebUI のタイトル生成などの裏処理がエージェントに来ないよう、裏処理は LLM に直接送る設定にする |

**デバッグ**

- Open WebUI から E-1（質問あり）と E-3（画像あり）を実行し、画面での見え方を確認する。
- 画像が Markdown で表示されるか（設計書 U-4）。

**レビューの合格条件**

- 画面から依頼 → 質問 → 回答 → 報告（画像付き）まで一通り動く。
- 研究室のメンバー 1〜2 人に使ってもらい、わかりにくい点を集める。

## 10. フェーズ 8: 評価と調整

**ゴール**: 設計書 12 章の比較実験を行い、本設計の効果を確かめ、上限や基準を調整する。

**やること**

- 3 通り（LLM 単体 / 横も縦も LLM の再帰 / 本設計）で全テストケースを実行し、指標を比べる。
- 結果を見て、止める条件（10.3）、画像の判定基準（8.3）、Tier の一覧を調整する。
- 結果を `docs/evaluation_<日付>.md` にまとめる。

**レビューの合格条件**

- 誤った画像を「確認済み」で出した数が 0。
- 比較実験の結果と、調整した内容・理由が文書になっている。

## 12. スケジュールの目安

研究の合間に進める想定で、1 フェーズ 1〜2 週間程度。フェーズ 1 までを最初の 2〜3 週間で終え、早めに「動くもの」を作る。
各フェーズの終わりに、うまくいかなかった点を次のフェーズの計画に反映する（計画は都度更新する）。
